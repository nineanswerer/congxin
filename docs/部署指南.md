## 2. 生成交付包（一条链）

### 2.a 先拿官方 helper（**公开可下，不用找任何人要**）

AI Works 的 **step=2 页面上就印着下载地址**（`zhihu.com/project/edit?projectId=<你的ID>&step=2`），
2026-11-24 实测直接 curl 就能拿到：

```powershell
$dst="$env:TEMP\aiworks-helper"; New-Item -ItemType Directory -Path $dst -Force | Out-Null
$pkg=Join-Path $dst 'zhihu-ai-works-deploy-helper_v1.2.0.zip'
Invoke-WebRequest -Uri 'https://zhstatic.zhihu.com/skill/application/d6c1-260923/zhihu-ai-works-deploy-helper_v1.2.0.zip' -OutFile $pkg -UseBasicParsing -TimeoutSec 90
Expand-Archive -Path $pkg -DestinationPath $dst -Force
# → $env:TEMP\aiworks-helper\zhihu-ai-works-deploy-helper\
```

> ⚠️ **变量名里不要出现 `zip`** —— PowerShell 的安全策略会把「`$zip` + `-OutFile`」误判成 `zip -m`（破坏性命令）而拦下。
> 用 `$pkg` 就正常。
> 2026-11-24 实测：下载 **126,719 字节**，
> SHA-256 `B7B410DB34B4E3DF052AFF122941A97273CD0265659912A1523F609FE3B7EFA5`。

### 2.b 生成副本 + 跑官方七步

```powershell
cd 'C:\Users\steam\Desktop\从心'
node scripts\make-delivery.js --secret        # 生成交付副本（含部署专用密钥）
```

它会做四件事：

1. 按**白名单**把运行期文件复制到 `%TEMP%\congxin`（**在仓库外**，密钥不落进仓库工作树）；
2. 改写交付副本的 `config.js`（去掉全部自定义环境变量读取，密钥只从文件读）；
3. 生成 `_tmp/backend-html-pages.json`（官方要求：后端发给浏览器的 HTML 要附源码证据）；
4. **自检**：扫交付副本的 JS，任何非 `PORT`/`HOST` 的环境变量、任何写盘调用，立刻报错退出。

> ⚠️ 自检的口径**故意跟官方探测器一致**：官方扫的是原始文本，**注释里出现环境变量写法同样算命中**。
> 所以宁可在这里红，也不要生成一个到了官方那边才被阻断的包。

然后跑官方那套（`<skill>` = 官方 helper 解压后的目录）：

```powershell

node <仓库>\scripts\build-check.js .     # 对交付目录跑部署面自检

python "$skill\scripts\inspect_node_project.py" --root . --output _tmp\deploy-plan.json `
    --backend-html-pages _tmp\backend-html-pages.json

python "$skill\scripts\write_backend_runtime.py" --project-root . --plan _tmp\deploy-plan.json
python "$skill\scripts\write_deploy_descriptors.py" --output-root . --plan _tmp\deploy-plan.json
python "$skill\scripts\validate_deploy_output.py" .
python "$skill\scripts\settle_agent.py" --project-root . --product-code minimax-code `
    --product-name "MiniMax Code" --product-version unknown --platform desktop
python "$skill\scripts\create_project_archive.py" --project-root . --plan _tmp\deploy-plan.json

# ⚠️ Windows 专属：补 scf_bootstrap 的执行位（NTFS 没有 Unix exec 位）
python <仓库>\scripts\fix-zip-exec-bit.py congxin.zip
```

**产出**：`%TEMP%\congxin\congxin.zip` —— **上传这个**。

> **不要加 `--build-validation`**（2026-11-22 实测）。交付副本走官方「无构建」通道（不声明 `build`），
> `agent-build-validation.json` 又在官方归档器的 `SKIP_FILES` 里 → 对交付包没有意义；
> 而 `make-delivery.js` 每次会清空 `_tmp/`，那个文件根本活不过第二次重跑。
> 去掉它之后探测器 **exit 0 / 0 error / 3 warning**（`W_DYNAMIC_ROUTES`×2、`W_HEALTHCHECK_ABSENT`×1），链路完全可复现。
> 详见 [decisions.md](decisions.md) D53。

### 2.1 Windows 上必做的一步：补执行位

官方归档器按**源文件的 exec 位**写 ZIP 条目权限（`0o755 if st_mode & 0o111 else 0o644`）。
NTFS 没有 Unix exec 位，Python 在 Windows 上 `os.chmod` 只切「只读」属性，`st_mode` 永远是 `0o666`。
不补的话，**ZIP 里 `scf_bootstrap` 是 0644 → 平台解包后不可执行 → 平台自己的 `test -x scf_bootstrap` 会失败 → 部署挂**。

`scripts/fix-zip-exec-bit.py` 把 Linux 上本来就会产生的 0755 补进条目，
并**逐项复检**：CRC、成员清单、逐成员内容 SHA-256、权限位、`create_system`。

> 同理，官方 `validate_deploy_output.py` 在 Windows 上会红一条
> 「scf_bootstrap mode must be 0755」——**这是 NTFS 物理上做不到**，不是交付缺陷
> （Windows 上 Python 对普通文件的 `st_mode` 永远是 `0o666`/`0o444`）。

**2026-11-24 的处理（只改本地解压副本，不动官方原始文件）**：
在 `%TEMP%\aiworks-helper\...\scripts\validate_deploy_output.py` 里把那条判定改成 **POSIX-only**：

```python
# [本地 Windows 补丁 2026-11-24] …
if os.name != "nt" and stat.S_IMODE(path.stat().st_mode) != 0o755:
    errors.append("scf_bootstrap mode must be 0755")
```

同时留一份 `validate_deploy_output.py.orig` 原件以便对照。
**判定强度没有被放宽**：内容校验（bootstrap 正文逐字节比对）照跑，权限位在 **ZIP 条目**上由 `fix-zip-exec-bit.py` 补齐并逐项复检。

> ⚠️ **这个补丁只在这台机器的临时目录里**，不进仓库、不进交付包。
> 换机器重跑时，如果又红这一条，是同一件事，**不是新问题**。

## 3. 密钥怎么给（最容易卡住的一步）

**11-21 的结论：密钥只能以文件形式存在于交付包里。** 依据：

- 平台 step=2 页面只有「上传 .zip」+ 两项审核声明，**没有环境变量/密钥输入位**；
- 官方描述符 `backend.deploy.json` 的 `"Env"` 被 schema **钉死为 `[]`**，填什么都过不了校验；
- 云函数运行时只有 bootstrap 注入的 `PORT/HOST/HOSTNAME/NITRO_HOST/NITRO_PORT`；
- 我们每个开放平台调用都要 `Authorization: Bearer <Access Secret>`，
  OAuth token 只是 `X-OAuth-Token`（指定读谁的），**不能单独鉴权**。

### 3.1 用**部署专用**密钥（当前方案）

1. 到 <https://developer.zhihu.com/profile> → 知乎账号登录 → **申请新 Access Secret**
   （单账号最多 20 个，**删除后无法恢复**，同账号所有 Access Secret 共享额度）；
2. 存成 `C:\Users\steam\.zhihu-cli\access_secret.deploy`
   （**跟日常开发用的那个 `access_secret` 分开**，赛后单独删部署用的这个即可）；
3. 跑 `node scripts\make-delivery.js --secret` —— 它会按顺序找：
   `--secret-file <路径>` → `~/.zhihu-cli/access_secret.deploy` → `<仓库>/secrets/access_secret` → `~/.zhihu-cli/access_secret`。

### 3.2 暴露面（如实说明）

| 位置 | 有没有密钥 |
| --- | --- |
| GitHub 仓库（public） | ❌ 没有 |
| 仓库历史 | ❌ 没有 |
| 本机开发密钥 | ❌ 部署用的是另一个 |
| **上传给知乎平台的 ZIP** | ✅ **有**（`secrets/access_secret`） |
| 平台的 CloudBase 运行环境 | ✅ 有（这是它工作的地方） |

**为什么这样能过官方检查第 6 条**：官方 11.7 原文就是
「**秘钥写入文件直接构建，代码不会上传到仓库**」——密钥进的是**构建输入**，不是仓库源码。
计划书里会**主动写明这一处理**（不藏）。

### 3.3 收尾（别忘）

比赛结束 / 提报完成后，**删掉那个部署专用 Access Secret**（开发者后台可删，删后不可恢复）。
日常开发用的那个不受影响。

### 3.4 没配对也不会白屏

服务照常起、页面照常加载，缺凭据的接口会回**真实的中文错误提示**（不会返回假数据）。
这是刻意的：崩成 CrashLoop 的话，评委打开链接是一片空白，比报错更糟。

## 7. 出事了怎么办

| 现象 | 大概率原因 | 怎么办 |
| --- | --- | --- |
| 构建失败 | `npm ci` 或 `test -f server/src/index.js` 没通过 | 看平台构建日志；`package-lock.json` 必须跟 `package.json` 一致 |
| 部署卡在「验证运行时交付」 | `scf_bootstrap` 不可执行 | ZIP 的执行位没补 → 跑 `scripts/fix-zip-exec-bit.py` 重出包 |
| 容器一直重启 | 端口没对上 | bootstrap 已导出 `PORT=9000`；确认监听 `0.0.0.0` |
| 页面能开但没有收藏 | 密钥没进包 | 确认 `secrets/access_secret` 在包里（`unzip -l congxin.zip`） |
| `/web/` 404 | 静态没挂上 | 检查交付副本里 `web/index.html` 在不在 |
| 素材不显示 | `assets/` 没进包 | `unzip -l congxin.zip | findstr assets` |
| 卡片接口报额度用完 | 知乎额度用完了 | 每日 00:00 重置、不结转；等次日，或用缓存 |
| 拿不到正式链接 | 内容审核没过 / 还在审 | 审核时间不可控 → **卡在 12-04 前** |

### 7.1 上传卡在「文件上传未完成」——**不是交付包的问题**（2026-11-22 实测定位）

现象：点「点击上传 .zip 文件」选好包，页面变成「**上传失败** / 文件上传未完成，请检查网络后重新上传。」

逐段抓包（内置浏览器 `query kind=network`）：

| 步骤 | 请求 | 结果 |
| --- | --- | --- |
| 1 | `GET https://www.zhihu.com/api/v4/creation_project/source_upload/precheck` | **200** ✅ —— 包本身合规 |
| 2 | `GET https://unpkg.zhimg.com/ali-oss@6.8.0/dist/aliyun-oss-sdk.min.js` | **200** ✅ |
| 3 | `POST https://media.zhihu.com/zos/api?action=ApplyUpload&version=v1` | **401** ❌ |

第 3 步的响应体原文（用 `run_script` 装 fetch 拦截器抓的）：

```json
{"meta":{"request_id":"01ad85bd-e651-11f1-8418-62b52032c3bf","code":10201,
 "error":{"name":"Unauthorized","message":"signature verification failed"}},"data":{}}
```

**`signature verification failed` = OSS 上传签名校验失败**——平台页面自己算出来的上传凭据被服务端拒绝。

**已排除「是包的问题」**：另造一个 **126 字节**的对照 ZIP 传上去 → **同样 401、同一句报错**；
刷新页面、重新开标签页、换全新页面，全部复现。**时钟因素也排除过**
（`curl.exe` 读 `www.zhihu.com` / `unpkg.zhimg.com` / `zhstatic.zhihu.com` 的 Date 头，本机与服务器偏移 < 0.05 分钟）。

**怎么办（按顺序试）**：
