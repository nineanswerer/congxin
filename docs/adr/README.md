# ADR — 决策记录

> 决策已经写在 [`docs/decisions.md`](../decisions.md)（D1—D24）。本目录是**同一套机制的扩展位**：
> 当某条决策值得单独展开（背景复杂、被否决的方案多、需要单独关联 commit）时，在这里开一份 ADR。
> **不要重复记录同一件事**：一条决策要么在 `decisions.md`，要么在 `adr/`，不要两边都写。

## 为什么要写这个

AI 最典型的翻车方式不是写错代码，而是**建议一个"更简洁"的写法，把某个隐藏约束悄悄破坏掉**。
比如把 `if score > 0.5 and len(text) > 10` 简化成 `if score > 0.5`，代码更干净，但短文本的处理逻辑没了。

ADR 的作用是：**把"为什么不那样写"钉死在仓库里**，让换 AI 平台、换人、三个月后回看时，
不用靠"读代码考古 + 猜对方意图"来恢复。

## 规则

1. **只增不改。** 决策变了就写新的一份 ADR，旧的那份把状态改成 `被取代`，正文一字不动。
2. **"被否决的方案"一节不许空。** 这一节是整套机制里最值钱的部分——它记录的是
   "我们试过、为什么放弃"。只写结论的 ADR 等于没写。
3. **每条至少一条可核对的依据。** 官方文档原文、本机实测数据、commit sha、issue 编号。
   没有依据的判断标 `依据：待验证`。
4. **关联到契约。** 如果这条决策改变了 `contracts/contract.json` 里的某一项，在 ADR 里写明是哪一项。
5. 编号用 `ADR-0001` 递增。生成：`powershell -ExecutionPolicy Bypass -File scripts/new-adr.ps1 <slug>`

## 状态取值

| 状态 | 含义 |
| --- | --- |
| 提议 | 还没定，讨论中 |
| 已采纳 | 生效中 |
| 已废弃 | 被更好的方案取代 |
| 被取代 | 被 ADR-XXXX 取代，正文保留 |

## 与 `docs/decisions.md` 的分工

| | `docs/decisions.md` | `docs/adr/` |
| --- | --- | --- |
| 粒度 | 一条一行结论 + 依据 + 状态 | 一份完整文档：背景 / 方案 / 被否决的方案 / 后果 |
| 适用 | 绝大多数决策（目前 D1—D24） | 背景复杂或被否决方案多的决策 |
| 读者 | 谁都能扫一眼 | 需要理解来龙去脉时 |
