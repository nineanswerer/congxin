## D6 · 四处工程硬伤必须改掉

- **日期**：2026-11-16
- **结论**：不采用队友提案中的以下写法。
  1. **网关超时后返回 mock_perfect_card.json** → 制造假成功。改为：失败时保留资料与进度，显示真实失败原因与可重试入口；模拟数据只允许出现在明确标注的演示模式。
  2. **`Promise.race` 超时** → 原任务仍可能继续运行并计费。需要真正的取消、迟到结果丢弃与任务预算（可复用《无提醒 Agent》里验证过的代际守卫思路）。

  4. **8 秒绝对超时 / 5 秒强制 FallbackRender** → 会把"慢"误判成"失败"，并触发上面的假成功路径。
- **依据**：评审"完成度"看 Demo 是否稳定运行；"AI 场景价值"看是否解决真实痛点。假成功会同时破坏这两项。

## D12 · 知乎能力主路径 = question recommend + question answers，直答仅作兜底

- **日期**：2026-11-16
- **结论**：桌宠"补知乎观点"的主链路 =
  `zhihu-cli question recommend --query '<资料主题>'` 找到相关知乎问题 → `zhihu-cli question answers --question-url '<完整URL>'` 取回答摘要与**原始回答链接** → 卡片挂上链接。`zhihu-cli answer`（直答）只用于快速解释与兜底。
- **依据**：
  - 官方 CLI 文档原文："搜索用于取得原始资料，直答用于快速获得总结。**深度研究、事实核查和观点比较不要用直答替代搜索**。"
  - 本产品的核心承诺是"每张卡片可回溯出处"。`question answers` 返回**原始回答链接**，`answer` 返回黑盒总结——前者才兑现承诺。
  - 额外价值：知乎问题本身就是"用户真实困惑"的集合，`question recommend` 让桌宠能发现"你这个主题下，知乎上有人在问什么"，这是 S2 获奖作品没有的角度。
- **状态**：已定

## D14 · 选题定位：桌宠是主体，知识卡片是产出物

- **日期**：2026-11-16
- **结论**：产品叙事的主次关系是——**桌宠是交互主体（有人格、有情绪、有反馈），知识卡片是它的产出物，知乎能力是它的信息来源。**
- **依据**：S2 一等奖 "MeetMind学脉" 已经占了"把收藏资料变成学习内容"这个位置（见 rules 13.1）。若主次颠倒——做一个"卡片生成器"再配个宠物皮肤——会被读成 MeetMind 的降级版，创新度（25%）直接失分。S3 首次单列"AI × 陪伴与交互"赛道，且上届无对等获奖形态，桌宠路线才是结构性机会。

  1. **有出处的观点对照**：卡片不只给 AI 摘要，而是给出**知乎上真实的不同答案及其链接**，让用户看到分歧本身。

## D15 · 后端直连知乎 HTTP API，不走官方 MCP

- **日期**：2026-11-16
- **结论**：Web 应用的后端直接调用 `https://developer.zhihu.com` 的 HTTP API，鉴权用 `Authorization: Bearer <Access Secret>` + `X-Request-Timestamp`；**不使用官方 MCP**。
- **依据**（由 zhihu-cli 0.6.3 `capabilities` 与官方 Skill `references/mcp.md` 核对）：
  - 官方只提供 4 个 MCP 服务：全网搜索、热榜、知乎搜索、直答。
  - 本项目主路径所需的 `question recommend`（`/api/v1/user/question_recommendations`）与 `question answers`（`/api/v1/content/question_answers`）**都没有 MCP 服务**。
  - 直答 HTTP 路径是 `/v1/chat/completions`，**OpenAI 兼容**，可直接用 OpenAI SDK 风格客户端接入。
- **附带结论**：直答有三档模型 `zhida-fast-1p5` / `zhida-thinking-1p5` / `zhida-agent`（智能检索与回答）。`zhida-agent` 与 D12 的原始链接路径**互补而非替代**——卡片挂原始链接做出处，综合解释交给 `zhida-agent`。
- **成本影响**：后端只需一个最小 Node 服务（Token 交换 + 代理 + 会话），**不需要任何数据库**（单进程进程内 Map 即可）。
- **状态**：已定

## D17 · 额度是本届的第一风险，缓存与额度监控是必做项

- **日期**：2026-11-16（实测发现）
- **结论**：
  1. **申请赛事专属额度是当前最高优先级的对外动作**（加官方助手 → 进官方群 → 领 800 美元 Token / 看山工作台额度）。
  2. 应用**必须**实现：请求缓存 + 请求去重 + 额度实时查询 + 额度耗尽的真实提示。官方文档把它写成最佳实践，在本届是生死线。
  3. 演示路径做**预生成缓存**，现场命中缓存；缓存未命中且额度耗尽时给真实提示，**绝不返回伪造数据**。
- **依据**（实测 `/api/v1/quota`）：普通自申请 Access Secret 的**直答只有 2 次/天、热榜 2 次/天**，而官网标称的黑客松额度是 100 次/天；搜索类 10 次/天 vs 标称 5000 次/天。差距 50—500 倍。
- **对方案的影响**：D12 的主路径（`question recommend` 10 次/天 + `question answers` 10 次/天）**在普通额度下勉强够用**；但直答与热榜在普通额度下**不可靠**，必须拿到赛事额度才能作为常规路径。
- **状态**：已定
