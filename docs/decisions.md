## D6 · 四处工程硬伤必须改掉

- **日期**：2026-11-16
- **结论**：不采用队友提案中的以下写法。
  1. **网关超时后返回 mock_perfect_card.json** → 制造假成功。改为：失败时保留资料与进度，显示真实失败原因与可重试入口；模拟数据只允许出现在明确标注的演示模式。
  2. **`Promise.race` 超时** → 原任务仍可能继续运行并计费。需要真正的取消、迟到结果丢弃与任务预算（可复用《无提醒 Agent》里验证过的代际守卫思路）。
  3. **原生弹窗即安全** → 系统级弹窗只能提升点击成本，不等于安全。删除类操作还缺路径范围校验、文件状态复核与恢复机制。Tauri 2 的插件 API 也与提案里的 `tauri::api::dialog::blocking::confirm` 写法不同。
  4. **8 秒绝对超时 / 5 秒强制 FallbackRender** → 会把"慢"误判成"失败"，并触发上面的假成功路径。
- **依据**：评审"完成度"看 Demo 是否稳定运行；"AI 场景价值"看是否解决真实痛点。假成功会同时破坏这两项。
- **状态**：已定

## D12 · 知乎能力主路径 = question recommend + question answers，直答仅作兜底

- **日期**：2026-11-16
- **结论**：桌宠"补知乎观点"的主链路 =
  `zhihu-cli question recommend --query '<资料主题>'` 找到相关知乎问题 → `zhihu-cli question answers --question-url '<完整URL>'` 取回答摘要与**原始回答链接** → 卡片挂上链接。`zhihu-cli answer`（直答）只用于快速解释与兜底。
- **依据**：
  - 官方 CLI 文档原文："搜索用于取得原始资料，直答用于快速获得总结。**深度研究、事实核查和观点比较不要用直答替代搜索**。"
  - 本产品的核心承诺是"每张卡片可回溯出处"。`question answers` 返回**原始回答链接**，`answer` 返回黑盒总结——前者才兑现承诺。
  - 额外价值：知乎问题本身就是"用户真实困惑"的集合，`question recommend` 让桌宠能发现"你这个主题下，知乎上有人在问什么"，这是 S2 获奖作品没有的角度。
- **状态**：已定

## D14 · 选题定位：桌宠是主体，知识卡片是产出物

- **日期**：2026-11-16
- **结论**：产品叙事的主次关系是——**桌宠是交互主体（有人格、有情绪、有反馈），知识卡片是它的产出物，知乎能力是它的信息来源。**
- **依据**：S2 一等奖 "MeetMind学脉" 已经占了"把收藏资料变成学习内容"这个位置（见 rules 13.1）。若主次颠倒——做一个"卡片生成器"再配个宠物皮肤——会被读成 MeetMind 的降级版，创新度（25%）直接失分。S3 首次单列"AI × 陪伴与交互"赛道，且上届无对等获奖形态，桌宠路线才是结构性机会。
- **由此产生的具体差异点**（写进计划书"核心创新"一栏）：
  1. **有出处的观点对照**：卡片不只给 AI 摘要，而是给出**知乎上真实的不同答案及其链接**，让用户看到分歧本身。
  2. **问题反哺**：桌宠能指出"你这个主题，知乎上正在被问的问题"，把用户的私人资料和公共讨论连起来。
  3. **陪伴而非工具**：桌宠对状态有反应（吞咽、思考、打盹、答错后的沮丧），它让"整理资料"这件事不再像 chores。
- **与队友《Agent Pet OS》白皮书 9 概念的对应关系**（谈判时用这张表，不是"推翻 vs 保留"）：
  | 白皮书概念 | 本方案处置 | 落到哪 |
  | --- | --- | --- |
  | 1 具身化智能体 | **保留** | 桌宠作为交互主体（D14 主次关系） |
  | 2 吞噬与知识内化 | **保留**（改实现） | 拖入资料 → 咀嚼（`eating`）→ 吐卡片（`emitting`）；双向链接改为带出处的卡片 |
  | 3 具象化建房子 | **保留**（大幅简化） | 卡片可归置的"小屋"视图 + 检索；不做自动双向链接图谱 |
  | 4 装备与专家系统 | 砍掉 | 需要插件 Schema + 沙箱执行器，收益不抵成本 |
  | 5 点头授权 | 砍掉 | 改为**显式确认 UI**，不做原生弹窗（原生弹窗不等于安全，见 D6） |
  | 6 多宠物生态 | 砍掉 | 首版只有一只宠物 |
  | 7 老板视角与多 Agent 团队 | 砍掉 | 真实任务不需要并发编排 |
  | 8 个人数字分身 | 砍掉 | 比赛期内无法证明"越用越准" |
  | 9 多平台与社交 / A2A | 砍掉 | 成本收益完全不成比例 |
  | **＋ 知乎作为信息来源**（新增） | **新增** | 差异点 1 / 2；也是 40% "AI 场景价值"的落点 |

  **结论：9 个概念保留 3 个、砍掉 6 个、新增 1 个。** 砍掉的 6 个是**与"一个具体任务里的学习搭子"无关的平台能力**，不是"不要桌宠"。
- **判据（用来终结争论的一句话）**：**把知乎整个拔掉，这个产品还成立吗？** 还成立（只少个信息源）→ 桌宠是皮肤；不成立（价值塌一半）→ 桌宠是主体。本项目选后者，因为 `question recommend` + `question answers` 是"卡片有出处、有分歧"的**唯一**来源（D12），拔掉知乎就没有 D14 的差异点 1 和 2。
- **评审影响**：形态 B 才能对标 S3 首次单列的"AI × 陪伴与交互"赛道（有 ¥2,000 的最佳交互陪伴奖）；形态 A 会被归到"AI × 知识与探索"，而那个位置 S2 一等奖 MeetMind学脉 已经占了。
- **状态**：待定（需与队友对齐，这是本项目最需要讨论的一件事）

## D15 · 后端直连知乎 HTTP API，不走官方 MCP

- **日期**：2026-11-16
- **结论**：Web 应用的后端直接调用 `https://developer.zhihu.com` 的 HTTP API，鉴权用 `Authorization: Bearer <Access Secret>` + `X-Request-Timestamp`；**不使用官方 MCP**。
- **依据**（由 zhihu-cli 0.6.3 `capabilities` 与官方 Skill `references/mcp.md` 核对）：
  - 官方只提供 4 个 MCP 服务：全网搜索、热榜、知乎搜索、直答。
  - 本项目主路径所需的 `question recommend`（`/api/v1/user/question_recommendations`）与 `question answers`（`/api/v1/content/question_answers`）**都没有 MCP 服务**。
  - 直答 HTTP 路径是 `/v1/chat/completions`，**OpenAI 兼容**，可直接用 OpenAI SDK 风格客户端接入。
- **附带结论**：直答有三档模型 `zhida-fast-1p5` / `zhida-thinking-1p5` / `zhida-agent`（智能检索与回答）。`zhida-agent` 与 D12 的原始链接路径**互补而非替代**——卡片挂原始链接做出处，综合解释交给 `zhida-agent`。
- **成本影响**：后端只需一个最小 Node 服务（Token 交换 + 代理 + 会话），**不需要任何数据库**（单进程进程内 Map 即可）。
- **状态**：已定

## D23 · 额度复查：新 Secret 额度无变化 → 按 10/2 的现实设计，PDF 解析改本地

- **日期**：2026-11-16 18:36
- **复查方式**：用户新建了一个 Access Secret 并提供；写入 `~/.zhihu-cli/access_secret`（gitignore）后调 `/api/v1/quota`，**HTTP 200**。

  | 能力 | 每日额度 | 已用 |
  | --- | --- | --- |
  | 全网搜索 / 知乎搜索 | 10 | 0 |
  | **问题发现**（`question recommend` + `question answers` 共用） | **10** | 1 |
  | **直答** | **2** | 1 |
  | **热榜** | **2** | 0 |

  | 知识库 / 创作能力 | 10 | 0 |
  | 知乎用户数据 | 1000 | 0 |

  → **报名 + 领取 800 美元看山积分，并没有提升开放平台额度。** 官网标称（搜索 5000/天、直答 100/天）与实测差 50—500 倍的**原因仍未查清**（账号等级？），但已排除"没领 Token"这个解释。**按最低额度做设计，不再等待额度变化。**

- **附带更正（2026-11-16 晚）**：此前把官网那组数字称作"官方免费额度"是**措辞不准**。官网 JSON 全文不含"免费""额度"二字，只有 `support.apis[].quota` 字段值；`developer.zhihu.com/docs?key=billing_price` 实抓是**模板占位页**；个人中心「用量统计」页我们**从未访问过**（该入口出自官方 Skill 文档）。精确出处见 [rules-知乎S3.md](rules-知乎S3.md) **14.7**。**结论不变：`/api/v1/quota` 返回多少，就按多少设计。**

- **结论 2**：**直答与热榜移出常规路径。**
  - 直答 2 次/天 → 不能作为卡片生成的常规能力，只保留作兜底与演示彩蛋。
  - 热榜 2 次/天 → **首版不做热榜功能**（不为了凑"11 类能力"而做一个每天崩一次的功能）。
  - 主路径 `question recommend` + `question answers` 共用 10 次/天 → **够演示，但不够多人试用** → 缓存 + 去重是硬需求，不是优化。

- **结论 3（范围变更）**：**PDF 解析改用前端本地解析，不再依赖官方 `tools` 额度。**
  - 理由：`tools` 只有 **2 次/天**，评委或试用者上传 PDF 基本必然失败 → 与"每张卡片可回溯原文"的验收条件直接冲突。
  - 做法：前端用 `pdfjs-dist` 纯客户端解析（不经过我们的后端，也**不把用户文件传到任何第三方**，这反而是隐私加分项）；后端仍保留官方 `tools` 通道作为可选能力。
  - 代价与风险：`pdfjs-dist` 增加约 1 MB 依赖；**中文 PDF 的文本提取存在字体编码坑**，可能提取为空。
  - **因此首版输入以「文本 / Markdown 粘贴」+「网页链接」为主，PDF 作为可选入口**，且 PDF 解析失败必须给**真实提示**（"这个 PDF 提取不到文字层，建议复制文本粘贴"），**绝不静默返回空卡片**。
  - 若队友坚持走官方 `tools` 额度，则必须接受"每天 2 次 PDF 解析"这个演示限制。**这一条需要与队友同步**（见 `docs/队友对齐清单.md`）。
  - 依据：AGENTS.md「新增依赖前先确认它解决的是已存在的问题」——这里已存在的问题就是 2 次/天的额度上限。

- **状态**：已定（结论 3 的 PDF 方案需队友知情；若队友选择官方 tools 路径，则回到"每天 2 次"的约束下重新排期）
