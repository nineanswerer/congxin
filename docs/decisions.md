## D6 · 四处工程硬伤必须改掉

- **日期**：2026-11-16
- **结论**：不采用队友提案中的以下写法。
  1. **网关超时后返回 mock_perfect_card.json** → 制造假成功。改为：失败时保留资料与进度，显示真实失败原因与可重试入口；模拟数据只允许出现在明确标注的演示模式。
  2. **`Promise.race` 超时** → 原任务仍可能继续运行并计费。需要真正的取消、迟到结果丢弃与任务预算（可复用《无提醒 Agent》里验证过的代际守卫思路）。
  3. **原生弹窗即安全** → 系统级弹窗只能提升点击成本，不等于安全。删除类操作还缺路径范围校验、文件状态复核与恢复机制。Tauri 2 的插件 API 也与提案里的 `tauri::api::dialog::blocking::confirm` 写法不同。
  4. **8 秒绝对超时 / 5 秒强制 FallbackRender** → 会把"慢"误判成"失败"，并触发上面的假成功路径。
- **依据**：评审"完成度"看 Demo 是否稳定运行；"AI 场景价值"看是否解决真实痛点。假成功会同时破坏这两项。

## D12 · 知乎能力主路径 = question recommend + question answers，直答仅作兜底

- **日期**：2026-11-16
- **结论**：桌宠"补知乎观点"的主链路 =
  `zhihu-cli question recommend --query '<资料主题>'` 找到相关知乎问题 → `zhihu-cli question answers --question-url '<完整URL>'` 取回答摘要与**原始回答链接** → 卡片挂上链接。`zhihu-cli answer`（直答）只用于快速解释与兜底。
- **依据**：
  - 官方 CLI 文档原文："搜索用于取得原始资料，直答用于快速获得总结。**深度研究、事实核查和观点比较不要用直答替代搜索**。"
  - 本产品的核心承诺是"每张卡片可回溯出处"。`question answers` 返回**原始回答链接**，`answer` 返回黑盒总结——前者才兑现承诺。
  - 额外价值：知乎问题本身就是"用户真实困惑"的集合，`question recommend` 让桌宠能发现"你这个主题下，知乎上有人在问什么"，这是 S2 获奖作品没有的角度。
- **状态**：已定

## D14 · 选题定位：桌宠是主体，知识卡片是产出物

- **日期**：2026-11-16
- **结论**：产品叙事的主次关系是——**桌宠是交互主体（有人格、有情绪、有反馈），知识卡片是它的产出物，知乎能力是它的信息来源。**
- **依据**：S2 一等奖 "MeetMind学脉" 已经占了"把收藏资料变成学习内容"这个位置（见 rules 13.1）。若主次颠倒——做一个"卡片生成器"再配个宠物皮肤——会被读成 MeetMind 的降级版，创新度（25%）直接失分。S3 首次单列"AI × 陪伴与交互"赛道，且上届无对等获奖形态，桌宠路线才是结构性机会。
- **由此产生的具体差异点**（写进计划书"核心创新"一栏）：
  1. **有出处的观点对照**：卡片不只给 AI 摘要，而是给出**知乎上真实的不同答案及其链接**，让用户看到分歧本身。
  2. **问题反哺**：桌宠能指出"你这个主题，知乎上正在被问的问题"，把用户的私人资料和公共讨论连起来。
  3. **陪伴而非工具**：桌宠对状态有反应（吞咽、思考、打盹、答错后的沮丧），它让"整理资料"这件事不再像 chores。
- **与队友《Agent Pet OS》白皮书 9 概念的对应关系**（谈判时用这张表，不是"推翻 vs 保留"）：
  | 白皮书概念 | 本方案处置 | 落到哪 |
  | --- | --- | --- |
  | 1 具身化智能体 | **保留** | 桌宠作为交互主体（D14 主次关系） |
  | 2 吞噬与知识内化 | **保留**（改实现） | 拖入资料 → 咀嚼（`eating`）→ 吐卡片（`emitting`）；双向链接改为带出处的卡片 |
  | 3 具象化建房子 | **保留**（大幅简化） | 卡片可归置的"小屋"视图 + 检索；不做自动双向链接图谱 |
  | 4 装备与专家系统 | 砍掉 | 需要插件 Schema + 沙箱执行器，收益不抵成本 |
  | 5 点头授权 | 砍掉 | 改为**显式确认 UI**，不做原生弹窗（原生弹窗不等于安全，见 D6） |
  | 6 多宠物生态 | 砍掉 | 首版只有一只宠物 |
  | 7 老板视角与多 Agent 团队 | 砍掉 | 真实任务不需要并发编排 |
  | 8 个人数字分身 | 砍掉 | 比赛期内无法证明"越用越准" |
  | 9 多平台与社交 / A2A | 砍掉 | 成本收益完全不成比例 |
  | **＋ 知乎作为信息来源**（新增） | **新增** | 差异点 1 / 2；也是 40% "AI 场景价值"的落点 |

  **结论：9 个概念保留 3 个、砍掉 6 个、新增 1 个。** 砍掉的 6 个是**与"一个具体任务里的学习搭子"无关的平台能力**，不是"不要桌宠"。
- **判据（用来终结争论的一句话）**：**把知乎整个拔掉，这个产品还成立吗？** 还成立（只少个信息源）→ 桌宠是皮肤；不成立（价值塌一半）→ 桌宠是主体。本项目选后者，因为 `question recommend` + `question answers` 是"卡片有出处、有分歧"的**唯一**来源（D12），拔掉知乎就没有 D14 的差异点 1 和 2。
- **评审影响**：形态 B 才能对标 S3 首次单列的"AI × 陪伴与交互"赛道（有 ¥2,000 的最佳交互陪伴奖）；形态 A 会被归到"AI × 知识与探索"，而那个位置 S2 一等奖 MeetMind学脉 已经占了。
- **状态**：**已定**（2026-11-17 队友对齐通过）
  - 对齐方式：2026-11-16 发出三问（画面主次 / 角色设定 / 方案文档能否公开），2026-11-17 队友回复"**可以，差不多**"，对"桌宠是主体、知识卡片是产出物"的主次关系无异议。
  - 队友对"GitHub 协作与两人分别使用不同 AI"提出疑虑，**该问题不影响 D14 结论本身**，处理方案见 **D25**。

## D15 · 后端直连知乎 HTTP API，不走官方 MCP

## D25 · 双 AI 协作：从"风险"改判为"资产"，用上下文四层把不确定性关进机制

- **日期**：2026-11-17
- **触发**：队友 2026-11-17 回复"可以，差不多"（D14 / D19 已对齐），同时对"**GitHub 上的版本提交 + 两个人分别使用不同 AI 平台**"提出疑虑。疑虑指向协作方式，不是产品方向。
- **结论**：
  1. **改判：两个 AI 平台是资产，不是风险。** 依据是官方明确建议保留 **AI 交互记录、设计底稿和开发日志**作为参赛材料；两条独立的 AI 轨迹本身就是创作佐证。而且**两个模型的盲区不同**——交叉审一次能捞出单模型审不出的问题（见 `prompts/CROSS_REVIEW.md`）。前提是上下文可控，而这正是下面机制要解决的。
  2. **落地"上下文四层"**（详见 [`docs/adr/ADR-0001-adopt-context-layers.md`](adr/ADR-0001-adopt-context-layers.md)）：
     - **L0 契约层** `contracts/contract.json` + `CONTRACTS.md`——不可变事实（赛程、额度、技术底座、合规红线），机器可读 + 脚本自检。
     - **L1 身份层** `AGENTS.md`——唯一真源。`CLAUDE.md` / `.cursor/rules/` / `.gemini/settings.json` / `.aider.conf.yml` / `.github/copilot-instructions.md` **全部只做指针**，不复制正文。
     - **L2 决策层** `docs/decisions.md` + `docs/adr/`——只增不改，"被否决的方案"不许空。
     - **L3 交接层** `docs/handoffs/`——每次会话一份，**让 AI 自己写，人只审阅**。
  3. **commit 三行由 hook 强制**（`.githooks/commit-msg`）：`Context:` / `Tried:` / `Verify:`。其中 **`Context:` 必须由人写**——AI 看得见 diff，但不知道"为什么"；硬写出来的 Context 只是 diff 的复述，看着煞有介事实则零信息量，还会污染下一个 AI 的判断。AI 负责标题与 `Tried:`。
  4. **目录所有权按目录分**：`nineanswerer` → `server/`、`docs/decisions.md`、`contracts/`；`5zdz5` → `web/`、`assets/`、`docs/adr/`、`docs/handoffs/`。共享区（`contracts/`、`docs/status.md`、`README.md`）走 PR，不直推 main；每天至少合并一次。
  5. **自检闸**：`scripts/check-contract.ps1` 检查文件齐全、AGENTS.md 行数上限、**疑似密钥扫描**、关键日期与 status.md 一致、hook 是否安装、是否有交接记录。**有 FAIL 不能提交。**
  6. **机制必须"不用人记得"——三条触发点全部自动化**（2026-11-17 补做，这是 D25 落地后的复查结论）：
     - **开工** → 各平台指针文件（`CLAUDE.md` / `.cursor/rules/00-project.mdc` / `.gemini/settings.json` / `.aider.conf.yml` / `.github/copilot-instructions.md`）被平台**自动加载**并指向 `prompts/BOOTSTRAP.md`，新 AI 自己读、自己复述、自己等确认。**换 AI 平台不再需要人手动粘贴 BOOTSTRAP。**
     - **拉取** → `.githooks/post-checkout` 在 `git pull` / `clone` / 切分支后**自动打印开工清单**，提醒"契约变了要重读"。**不再依赖人记得。**
     - **收工** → 开工协议的「收工协议」段写明：AI 自己写交接到 `docs/handoffs/`、自己跑自检。**不再需要人提醒。**
     - **提交** → `Context:` 行仍由人给，但**人不用手改 commit message**：AI 把人明确说过的理由转录进 `.ctx/current.md`（已 gitignore），`commit-msg` hook 在 `Context:` 缺失时自动填入，提交后自动清空。**AI 只转录不许推断。**
     - → **人真正要做的只剩一件事：跟 AI 说清"为什么改"**，一句话。
  7. **自检脚本同步扩到 10 项**，新增：各平台指针文件是否都能走到开工协议（验**指针链**，不是验关键词）、post-checkout 是否带开工清单、`.ctx/` 是否已 gitignore。
- **被否决的方案**（详见 ADR-0001）：
  - **A. 只靠 GitHub 版本控制**——Git 记 diff，不记"为什么"和"试过什么失败了"。换平台必然重建上下文，且重建时"猜得很自信"。
  - **B. 全队统一到一个 AI 平台**——表面消除了上下文割裂，实则把风险换成单点：一人账号/额度/模型变动即全队停摆，且放弃双模型交叉审查这一优势。
  - **C. 外部 wiki / 第三方知识库**——赛规未要求，且引入平台外账号依赖与同步延迟；`docs/` 已在 Git 里，天然带版本与评审。
  - **D. 直接搬用云端会话里产出的通用 kit**（`zhihu-s3-context-kit`）——该 kit 主体为 Linux bash 脚本（本项目是 Windows/PowerShell），且自带 `AGENTS.md` 会覆盖本项目规则，违反本项目 AGENTS.md 第 1 节"唯一真源"。**改为按同样设计意图为本仓库重做。**
- **依据**：
  - 官方建议保留 AI 交互记录、设计底稿和开发日志（见 [rules-知乎S3.md](rules-知乎S3.md)）。
  - 本仓库实测：`scripts/check-contract.ps1` PASS 8 / WARN 0 / FAIL 0；commit-msg hook 实测**空洞提交被拒、`Tried:` 为空被拒、格式正确放行**。
  - 云端会话 `464028321079849` 产出的通用 kit（作为**设计参考**，非代码来源）。
- **状态**：**机制已定并落地**（文件已入仓，自检与 hook 均实跑通过）；**目录分工与"共享区走 PR"规则尚待队友本人确认**（见 `docs/handoffs/2026-11-17-1233-首次协作机制落地.md` 第 6 节）。

### 落地的四条硬约束

1. **出处三件套必填**：问题标题 + 问题 URL + **原回答 URL**。

   （官方提交前检查第 6、7 条查的就是没有出处的卡片）。
2. **不写死素材**：主题来自请求参数（用户拖进来那份资料是关于什么的），每次跑都是**实时**知乎数据。
3. **空数据 ≠ 失败**：上游捞不到 → 200 + `empty: true` + 中文 `empty_notice`，`cards` 给空数组（不是 null）。
4. **卡片与情境题共用检索链路**（省人时的第 2 条决定）：抽出 `server/src/services/retrieval.js`，
   `services/cards.js` 与 `services/situation.js` 都走它——**检索只做一次**，下游两种投影。

### 实测结论：卡片**只能**走「问题发现」链路

逐个查过上游能不能给全三元组：

| 上游 | 能不能给「问题标题 + 问题 URL + 原回答 URL」 |
| --- | --- |
| `user/collections`（收藏，user_data 10000/天） | ❌ 实测该账号 9 条收藏里 **8 条是专栏文章**（`zhuanlan.zhihu.com/p/...`），剩下 1 条的 URL 是 `zhuanlan` 之外的 `zhihu.com/answer/xxx` 形式——**推不出问题 URL**，也没有原回答 URL |
| `user/favlist_contents` | ❌ 同上（同一套 item 形状） |
| `zhihu_search` | ❌ 给得了问题标题与问题 URL，**给不了原回答 URL** |
| `content/question_answers`（问题发现 100/天） | ✅ 它的 `Url` 字段就是**原回答链接** |

→ **原回答 URL 只有 `question_answers` 能给**，所以「能用收藏就别用问题发现」这条偏好
**让位**给出处硬约束（后者是赛规硬约束）。
→ 代价用缓存摊平：**按主题缓存 5 分钟**（`lib/cache.js` 的 `cached()`，顺带请求去重）
+ **回答按问题 URL 单独缓存** → **要几张卡才花几次**上游，不会因为池子是 20 个候选就多打。

第二次调用命中缓存（同一个 id、不再打上游）。

### 结论 2 · **主流程那张卡片换成契约里的真卡片**

## D37 · 「吵起来的两边」= **同一个知乎问题下的两条回答**（契约 v0.6）

- **时间**：2026-11-19 12:5x—13:0x
- **拍板人**：用户（2026-11-19「改后端做成真两方」）
- **关联**：ADR-0002 · `contracts/api.json` v0.5 → v0.6 · `POST /api/cards`

### 背景（事实）

P1 脚本 1:45—2:45 要「**2 张观点卡，来自两个不同的人，观点相反**」，台词是契约里定死的
「知乎上吵起来的两边，我都带来了」「它们说的是反的」。

但 `POST /api/cards` 的语义是「**一个候选问题取一条回答**」→ 「知乎上大家怎么说」拿到的是
**同主题的两个不同问题**（11-18 实测：「有没有知名度不高，好用的的软件啊？」+
「你使用过最好的AI软件推荐?」），**数据层根本没验证过两边是对立的**。
**台词在说一件数据没支撑的事**——评审面前会被问穿。

三条硬约束：

1. 「问题发现」额度 100 次/天，**不能为了凑出对立去多刷上游**。
2. **上游回答对象只有 4 个字段**（`ContentType` / `ContentToken` / `Url` / `Summary`，
   11-19 实测原始响应）——**没有作者、没有立场**。
3. 契约 v0 是冻结的（D28），改契约要走 ADR + 自检，且**不能破坏已有请求的行为**。

### 结论 1 · `POST /api/cards` 加**可选**参数 `same_question`

- 传 `true` → 返回的卡片全部来自**同一个知乎问题下的不同回答**
  （`source.question_url` 相同、`source.answer_url` 不同）。
- 不传（或 `false`）→ **行为一个字都没变**：N 个不同问题，各取第 1 条能用的回答。
- 契约 `api.json` v0.5 → **v0.6**，**14 个路径不变**；`contract.json` 的 `api_contract` 同步 + 规则 1 条。
- **前端**：`loadViewpoints()` 走 `same_question: true`；`renderViews()` 认出同题 →
  面板标题改成「**同一个问题的两条回答**」，**问题标题只出现一次**，两张卡标成「回答 ①/②」。

### 结论 2 · 额度**反而省 1 次**

上游 `content/question_answers` **一次调用就返回该问题下的 3 条回答**（`Limit=3`），
而原实现 `firstAnswerWithUrl` **只用了第 1 条**。把缓存改成**按问题 URL 缓存回答列表**后：

| 模式 | 花几次问题发现 |
| --- | --- |
| 默认（N 个不同问题） | 1 + N |
| 同题两答（1 个问题取 N 条） | **1 + 1** |

→ 同题两答**不多花额度，反而少 1 次**；两种模式**共用同一次上游调用**（同一个缓存池）。

### 结论 3 · **上游天花板**：「来自两个不同的人」「观点相反」**验证不了**

上游只给 4 个字段，**没有作者、没有立场**。所以：

- 「**同题两答**」是**结构上可证的**（同一个问题、不同的回答）。
- 「**作者是谁**」「**观点是否相反**」**数据层给不出** → 谁在文案里假装有，谁就是在编。
- 台词「它们说的是反的」仍属**视觉暗示**（P1 脚本原话：「只做视觉暗示，不解释」）。
- **界面只写可证的事实**（「同题 · 两条真实回答」），**不写「来自两个人」**。
- 等上游哪天能给出作者或立场，再把「对立」做成**可验证**的，并同步改 `contracts/tone.json` 的 `disagree`。

### 验证（实跑，2026-11-19）

- `POST /api/cards {"topic":"长期主义","count":2,"same_question":true}` → **同一个问题**下的两条回答
  （`question/2023732891524310793`，两个不同 `answer_url`）。
- 默认模式回归：`{"topic":"软件测试","count":3}` → **三个不同问题**（没被改坏）。
- `node server/scripts/smoke-cards.js` → 加了断言并**实跑全绿**（同题 / 不同回答 / id 不同 / 出处三件套 / 契约有 `same_question`）。

  台词依次是「知乎上吵起来的两边，我都带来了——原话，附链接。」→「它们说的是反的。我不替你选。」

## D39 · 桌宠「白边 + 残留影像」：根因是**转码与容器封装**，不是官方素材画风（撤销 11-19 早先结论）

- **关联**：D19 · `assets/kanshan/NOTICE.md` · `scripts/build-kanshan-assets.js` · `web/css/app.css`

### 背景：先撤回一个错误结论

11-19 13:2x，本会话给用户的结论是「**残留影像是官方素材本身、改不了**」，
依据是「用 Pillow 把 `greet.webp` 拆成单帧 PNG，第 10/20/30/35 帧里本来就画着好几只手臂」。

**用户不接受这个结论**，要求继续查。**用户坚持的方向是对的——错的是我。**

**为什么当时会判断错**：Pillow 的 `im.seek(i)` 给的是**合成帧**，
把动画 WebP 的累积结果当成了「这一帧的原始画面」。
**判定素材真伪只能靠浏览器直接加载官方原始 GIF 对照，不能靠拆动画 WebP。**

### 结论 1 · 三层根因，逐层定位

| 层 | 现象 | 真因 | 证据 |
| --- | --- | --- | --- |
| ① 素材转码 | 手臂拖影**烤进帧里** | 旧命令 `fps=10` 是恒定帧率滤镜，会**混合相邻帧** | 官方 GIF 解码胶片条每帧一只手臂；转码后每帧多只手 |
| ② 容器封装 | **越播越重**（白边 + 残影累积） | ffmpeg/libwebp 对动画一律写 `dispose=none + blend=alpha`，而素材是**透明背景** → 第 N 帧叠在第 N-1 帧上 | ANMF 帧头 flags 实测 `dispose=0`；官方 GIF 同一时刻干净 |
| ③ CSS 合成 | 白边 | `filter` / transform 动画直接作用在**动画 WebP 的 `<img>`** 上，Chrome 逐帧重新合成 | 修 CSS 后 `<img>` 的 computed filter/transform 均为 none |

**② 才是「越来越重」的直接原因**——旧素材在 HEAD 里**同样是 `dispose=0`**
（`git show HEAD:assets/kanshan/*.webp` 逐个解析确认），**不是新转码引入的，是一直如此**。

### 结论 2 · 改法与可复现链路

1. **丢帧不混合**：`select=not(mod(n\,2)),setpts=N/(10*TB)`，严格 10fps。
2. **保持原始 320×320**（页面按 210px 显示，缩到 160 反而更糊），质量 q78 → **q92**。
3. **帧处置补丁**：每个 ANMF 头的 dispose 由 0 改成 1（还原到背景）——
   ffmpeg 没有对应开关，只能改容器标志位，**只改标志位、不动像素**。
4. 全部收敛到一个脚本：**`scripts/build-kanshan-assets.js`**（跑完打印帧数 / 帧矩形 / dispose 自检）。

**体积**：6 个动画合计 **1222 KB**（旧版 942 KB；官方原始 GIF 5692 KB）。

### 结论 3 · 撤销先前结论

`docs/status.md` 13:3x 那条「⚠️「残留影像」查明是官方素材本身，不是渲染 bug（改不了）」

- **再加一道安全网**：`ApiError.toBody()` 统一过一遍 `scrubDetail()`，

  并把卡片已经用过的知乎问题 URL 传给 `answered_sources`，**情境题必须是另一个真问题**。
- **实测**：情境题从「基金 30 年定投」变成知乎原问题「**新人如何入门和学习软件测试？**」，

3. **不改前端、不改接口契约、不改产品形态** —— 契约仍是 14 个路径，台词仍是 14 句。

## D50 · Windows 上必须补 ZIP 执行位 + 交付版走「无构建」通道

- **时间**：2026-11-21
- **拍板人**：本会话（工具链适配，无业务取舍）
- **关联**：D48 · `scripts/fix-zip-exec-bit.py` · `scripts/make-delivery.js`

### 背景

官方 `validate_deploy_output.py` 要求 `scf_bootstrap` 的**文件模式是 0755**，而官方归档器写 ZIP 条目权限时取的是
**源文件的 exec 位**：`mode = 0o755 if source.stat().st_mode & 0o111 else 0o644`。

我们在 **Windows / NTFS** 上准备交付包：**NTFS 没有 Unix exec 位**，Python 的 `os.chmod` 在 Windows 上只切「只读」属性，
`st_mode` 恒为 `0o666`（已实测：`chmod 0755` 之后仍是 `0o666`）。WSL 的 vhdx 已损坏（`ERROR_PATH_NOT_FOUND`），
本机也没有 Docker。

**这不是一个无关紧要的校验红字**：ZIP 里 `scf_bootstrap` 若成了 0644 → 平台解包后启动文件不可执行 →
平台自己的校验步骤 `test -x scf_bootstrap` 失败 → **部署直接挂**。

### 结论

1. **`scripts/fix-zip-exec-bit.py`**：把「Linux 上本来就会产生的 0755」补进 ZIP 条目，
   并在写完后**逐项复检**——CRC（`testzip()`）、成员清单与顺序、**逐成员内容 SHA-256**、
   权限位、`create_system == 3`（否则 Linux 解包会忽略权限位）。
   这不是「改了就交差」，是**可复检的等效实现**。
2. **官方校验器在 Windows 上会红一条**「scf_bootstrap mode must be 0755」——
   **这是 NTFS 物理上做不到，不是交付缺陷**；其余检查全过，且这个权限已在 ZIP 里补齐。**如实记录，不谎称全绿。**
3. **交付版不带 `build` 脚本**（理由见 D48）：走官方「无构建」通道，构建步骤 = `test -f server/src/index.js`。

### 状态

**已定并实施**。交付 ZIP 实测：`scf_bootstrap` = **0755**、其余 64 个成员全 0644、
无 `node_modules` / `docs` / 开发脚本 / 密钥 / `.env`。

## D62 · 失败态只说真话：「读不到」不等于「0」，「没找到断层」不等于「两边一致」

### 背景

P5「拟真 + 失败态」要验的是官方检查第 7 条：**接口失败、额度耗尽、空数据必须有真实提示**。
逐个手动点验的时候，挖出**两处「假陈述」** —— 它们说的都不是假话，但**把「读不到」说成了「没有」**。

**其一：读不到知乎数据的时候，界面印的是 `0`。**

| 位置 | 原来印的 | 真相 |
| --- | --- | --- |
| 日报头版「收藏条数」 | `0` | **读不到**（≠ 你没收藏） |
| 日报索引标题 | 「你收藏 / 读过的 0 条」 | 读不到 |
| 日报「阅读版图」 | 「暂无分类数据」 | **分类读不到**（≠ 没有分类） |
| 日报脚注 | 没说话 | 整期没印出来，得说清楚 |
| 页头额度 pill | 「额度没读到」 | 是事实，**但不给原因是没用的真话** |

最后一条最典型：用户看到「额度没读到」，无从判断是**额度用完了、凭据坏了、还是网络抖** ——
所以它虽然不算撒谎，却**没能提供任何可行动的信息**。

**其二：自述侧压根没说自己重什么，界面却印「两边一致」。**

后端 `buildTension()` 的断层判定是关键词级的：自述侧出现「深度型 / 关系型 / 输出型」词，才拿它跟行为侧比。
枚举 3^6 = **729 种答法**后发现：**有 16 种（2.2%）**的 traits 里**一个可比维度都没有** ——
典型是全选「先做出一个能跑的版本 / 能不能跑通 / 怎么用起来 / 攒了很多但基本没再看 / 推进得快 / 交付了能用的东西」
这类，说的全是「**怎么做**」，没有一句说「**你是什么样的人**」。

这时 fractures 必为空 → 前端落到 `!data.has_tension` 分支 → 印「**没找到断层。你说的和你做的在这几个维度上是一致的**」 ——
**这是假陈述**：用户压根没说过自己重什么，**无从比较**，「一致」是他没说过话之后被替他说出来的。
跟 D60 修掉的「一个字没答就下判断」是同一类错误。

### 决定

1. **「读不到」一律不许印成 `0`。** 收藏条数、阅读跨度、两个额度，在读不到时印 `—`；
   索引标题改「今天读不到知乎上的收藏」；分类区改「分类读不到（不是「没有分类」）」；
   脚注改「这一期的数据没印出来 —— 上面写着的是读不到的原因，不是一份空的日报」。
   —— 界面可以不好看，但**每句话都得站得住**。
2. **没用的真话要换成有用的真话。** 额度 pill 的 catch 不再写「额度没读到」，
   改成直接显示**后端错误信封里那句 `user_hint`**（跟 `showFail` 同一个口径），**一句都不另编**。
3. **自述侧无可比维度 → 走 `insufficient`，不许印「一致」。** 后端新增判定：
   `insufficient: true` + `insufficient_reason` 说清「**是你这边没说清，不是两边一致**」，
   并在 `warnings` 里加 `self_report_not_comparable`；前端按 `warnings` 区分标题
   （「你还没说清自己重什么。」/「信号不够，断层不成立。」）。
