## D6 · 四处工程硬伤必须改掉

- **日期**：2026-11-16
- **结论**：不采用队友提案中的以下写法。
  1. **网关超时后返回 mock_perfect_card.json** → 制造假成功。改为：失败时保留资料与进度，显示真实失败原因与可重试入口；模拟数据只允许出现在明确标注的演示模式。
  2. **`Promise.race` 超时** → 原任务仍可能继续运行并计费。需要真正的取消、迟到结果丢弃与任务预算（可复用《无提醒 Agent》里验证过的代际守卫思路）。
  3. **原生弹窗即安全** → 系统级弹窗只能提升点击成本，不等于安全。删除类操作还缺路径范围校验、文件状态复核与恢复机制。Tauri 2 的插件 API 也与提案里的 `tauri::api::dialog::blocking::confirm` 写法不同。
  4. **8 秒绝对超时 / 5 秒强制 FallbackRender** → 会把"慢"误判成"失败"，并触发上面的假成功路径。
- **依据**：评审"完成度"看 Demo 是否稳定运行；"AI 场景价值"看是否解决真实痛点。假成功会同时破坏这两项。

## D12 · 知乎能力主路径 = question recommend + question answers，直答仅作兜底

- **日期**：2026-11-16
- **结论**：桌宠"补知乎观点"的主链路 =
  `zhihu-cli question recommend --query '<资料主题>'` 找到相关知乎问题 → `zhihu-cli question answers --question-url '<完整URL>'` 取回答摘要与**原始回答链接** → 卡片挂上链接。`zhihu-cli answer`（直答）只用于快速解释与兜底。
- **依据**：
  - 官方 CLI 文档原文："搜索用于取得原始资料，直答用于快速获得总结。**深度研究、事实核查和观点比较不要用直答替代搜索**。"
  - 本产品的核心承诺是"每张卡片可回溯出处"。`question answers` 返回**原始回答链接**，`answer` 返回黑盒总结——前者才兑现承诺。
  - 额外价值：知乎问题本身就是"用户真实困惑"的集合，`question recommend` 让桌宠能发现"你这个主题下，知乎上有人在问什么"，这是 S2 获奖作品没有的角度。
- **状态**：已定

## D14 · 选题定位：桌宠是主体，知识卡片是产出物

- **日期**：2026-11-16
- **结论**：产品叙事的主次关系是——**桌宠是交互主体（有人格、有情绪、有反馈），知识卡片是它的产出物，知乎能力是它的信息来源。**
- **依据**：S2 一等奖 "MeetMind学脉" 已经占了"把收藏资料变成学习内容"这个位置（见 rules 13.1）。若主次颠倒——做一个"卡片生成器"再配个宠物皮肤——会被读成 MeetMind 的降级版，创新度（25%）直接失分。S3 首次单列"AI × 陪伴与交互"赛道，且上届无对等获奖形态，桌宠路线才是结构性机会。
- **由此产生的具体差异点**（写进计划书"核心创新"一栏）：
  1. **有出处的观点对照**：卡片不只给 AI 摘要，而是给出**知乎上真实的不同答案及其链接**，让用户看到分歧本身。
  2. **问题反哺**：桌宠能指出"你这个主题，知乎上正在被问的问题"，把用户的私人资料和公共讨论连起来。
  3. **陪伴而非工具**：桌宠对状态有反应（吞咽、思考、打盹、答错后的沮丧），它让"整理资料"这件事不再像 chores。
- **与队友《Agent Pet OS》白皮书 9 概念的对应关系**（谈判时用这张表，不是"推翻 vs 保留"）：
  | 白皮书概念 | 本方案处置 | 落到哪 |
  | --- | --- | --- |
  | 1 具身化智能体 | **保留** | 桌宠作为交互主体（D14 主次关系） |
  | 2 吞噬与知识内化 | **保留**（改实现） | 拖入资料 → 咀嚼（`eating`）→ 吐卡片（`emitting`）；双向链接改为带出处的卡片 |
  | 3 具象化建房子 | **保留**（大幅简化） | 卡片可归置的"小屋"视图 + 检索；不做自动双向链接图谱 |
  | 4 装备与专家系统 | 砍掉 | 需要插件 Schema + 沙箱执行器，收益不抵成本 |
  | 5 点头授权 | 砍掉 | 改为**显式确认 UI**，不做原生弹窗（原生弹窗不等于安全，见 D6） |
  | 6 多宠物生态 | 砍掉 | 首版只有一只宠物 |
  | 7 老板视角与多 Agent 团队 | 砍掉 | 真实任务不需要并发编排 |
  | 8 个人数字分身 | 砍掉 | 比赛期内无法证明"越用越准" |
  | 9 多平台与社交 / A2A | 砍掉 | 成本收益完全不成比例 |
  | **＋ 知乎作为信息来源**（新增） | **新增** | 差异点 1 / 2；也是 40% "AI 场景价值"的落点 |

  **结论：9 个概念保留 3 个、砍掉 6 个、新增 1 个。** 砍掉的 6 个是**与"一个具体任务里的学习搭子"无关的平台能力**，不是"不要桌宠"。
- **判据（用来终结争论的一句话）**：**把知乎整个拔掉，这个产品还成立吗？** 还成立（只少个信息源）→ 桌宠是皮肤；不成立（价值塌一半）→ 桌宠是主体。本项目选后者，因为 `question recommend` + `question answers` 是"卡片有出处、有分歧"的**唯一**来源（D12），拔掉知乎就没有 D14 的差异点 1 和 2。
- **评审影响**：形态 B 才能对标 S3 首次单列的"AI × 陪伴与交互"赛道（有 ¥2,000 的最佳交互陪伴奖）；形态 A 会被归到"AI × 知识与探索"，而那个位置 S2 一等奖 MeetMind学脉 已经占了。
- **状态**：**已定**（2026-11-17 队友对齐通过）
  - 对齐方式：2026-11-16 发出三问（画面主次 / 角色设定 / 方案文档能否公开），2026-11-17 队友回复"**可以，差不多**"，对"桌宠是主体、知识卡片是产出物"的主次关系无异议。
  - 队友对"GitHub 协作与两人分别使用不同 AI"提出疑虑，**该问题不影响 D14 结论本身**，处理方案见 **D25**。

## D15 · 后端直连知乎 HTTP API，不走官方 MCP

## D25 · 双 AI 协作：从"风险"改判为"资产"，用上下文四层把不确定性关进机制

- **日期**：2026-11-17
- **触发**：队友 2026-11-17 回复"可以，差不多"（D14 / D19 已对齐），同时对"**GitHub 上的版本提交 + 两个人分别使用不同 AI 平台**"提出疑虑。疑虑指向协作方式，不是产品方向。
- **结论**：
  1. **改判：两个 AI 平台是资产，不是风险。** 依据是官方明确建议保留 **AI 交互记录、设计底稿和开发日志**作为参赛材料；两条独立的 AI 轨迹本身就是创作佐证。而且**两个模型的盲区不同**——交叉审一次能捞出单模型审不出的问题（见 `prompts/CROSS_REVIEW.md`）。前提是上下文可控，而这正是下面机制要解决的。
  2. **落地"上下文四层"**（详见 [`docs/adr/ADR-0001-adopt-context-layers.md`](adr/ADR-0001-adopt-context-layers.md)）：
     - **L0 契约层** `contracts/contract.json` + `CONTRACTS.md`——不可变事实（赛程、额度、技术底座、合规红线），机器可读 + 脚本自检。
     - **L1 身份层** `AGENTS.md`——唯一真源。`CLAUDE.md` / `.cursor/rules/` / `.gemini/settings.json` / `.aider.conf.yml` / `.github/copilot-instructions.md` **全部只做指针**，不复制正文。
     - **L2 决策层** `docs/decisions.md` + `docs/adr/`——只增不改，"被否决的方案"不许空。
     - **L3 交接层** `docs/handoffs/`——每次会话一份，**让 AI 自己写，人只审阅**。
  3. **commit 三行由 hook 强制**（`.githooks/commit-msg`）：`Context:` / `Tried:` / `Verify:`。其中 **`Context:` 必须由人写**——AI 看得见 diff，但不知道"为什么"；硬写出来的 Context 只是 diff 的复述，看着煞有介事实则零信息量，还会污染下一个 AI 的判断。AI 负责标题与 `Tried:`。
  4. **目录所有权按目录分**：`nineanswerer` → `server/`、`docs/decisions.md`、`contracts/`；`5zdz5` → `web/`、`assets/`、`docs/adr/`、`docs/handoffs/`。共享区（`contracts/`、`docs/status.md`、`README.md`）走 PR，不直推 main；每天至少合并一次。
  5. **自检闸**：`scripts/check-contract.ps1` 检查文件齐全、AGENTS.md 行数上限、**疑似密钥扫描**、关键日期与 status.md 一致、hook 是否安装、是否有交接记录。**有 FAIL 不能提交。**
  6. **机制必须"不用人记得"——三条触发点全部自动化**（2026-11-17 补做，这是 D25 落地后的复查结论）：
     - **开工** → 各平台指针文件（`CLAUDE.md` / `.cursor/rules/00-project.mdc` / `.gemini/settings.json` / `.aider.conf.yml` / `.github/copilot-instructions.md`）被平台**自动加载**并指向 `prompts/BOOTSTRAP.md`，新 AI 自己读、自己复述、自己等确认。**换 AI 平台不再需要人手动粘贴 BOOTSTRAP。**
     - **拉取** → `.githooks/post-checkout` 在 `git pull` / `clone` / 切分支后**自动打印开工清单**，提醒"契约变了要重读"。**不再依赖人记得。**
     - **收工** → 开工协议的「收工协议」段写明：AI 自己写交接到 `docs/handoffs/`、自己跑自检。**不再需要人提醒。**
     - **提交** → `Context:` 行仍由人给，但**人不用手改 commit message**：AI 把人明确说过的理由转录进 `.ctx/current.md`（已 gitignore），`commit-msg` hook 在 `Context:` 缺失时自动填入，提交后自动清空。**AI 只转录不许推断。**
     - → **人真正要做的只剩一件事：跟 AI 说清"为什么改"**，一句话。
  7. **自检脚本同步扩到 10 项**，新增：各平台指针文件是否都能走到开工协议（验**指针链**，不是验关键词）、post-checkout 是否带开工清单、`.ctx/` 是否已 gitignore。
- **被否决的方案**（详见 ADR-0001）：
  - **A. 只靠 GitHub 版本控制**——Git 记 diff，不记"为什么"和"试过什么失败了"。换平台必然重建上下文，且重建时"猜得很自信"。
  - **B. 全队统一到一个 AI 平台**——表面消除了上下文割裂，实则把风险换成单点：一人账号/额度/模型变动即全队停摆，且放弃双模型交叉审查这一优势。
  - **C. 外部 wiki / 第三方知识库**——赛规未要求，且引入平台外账号依赖与同步延迟；`docs/` 已在 Git 里，天然带版本与评审。
  - **D. 直接搬用云端会话里产出的通用 kit**（`zhihu-s3-context-kit`）——该 kit 主体为 Linux bash 脚本（本项目是 Windows/PowerShell），且自带 `AGENTS.md` 会覆盖本项目规则，违反本项目 AGENTS.md 第 1 节"唯一真源"。**改为按同样设计意图为本仓库重做。**
- **依据**：
  - 官方建议保留 AI 交互记录、设计底稿和开发日志（见 [rules-知乎S3.md](rules-知乎S3.md)）。
  - 本仓库实测：`scripts/check-contract.ps1` PASS 8 / WARN 0 / FAIL 0；commit-msg hook 实测**空洞提交被拒、`Tried:` 为空被拒、格式正确放行**。
  - 云端会话 `464028321079849` 产出的通用 kit（作为**设计参考**，非代码来源）。
- **状态**：**机制已定并落地**（文件已入仓，自检与 hook 均实跑通过）；**目录分工与"共享区走 PR"规则尚待队友本人确认**（见 `docs/handoffs/2026-11-17-1233-首次协作机制落地.md` 第 6 节）。

  - **这是决策稿里没有的第三个选项**（原决策稿只有「换成认知地形」与「维持学习桌宠」两个）。它优于那两个：
