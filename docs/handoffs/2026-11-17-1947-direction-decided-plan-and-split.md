## 3. 试过但没成的（**最重要，别省**）

### 3.1 ⚠️ **多行 `edit` 的 old_string 匹配会失败（本次最贵的坑）**

在 `contracts/api.json` 和 `docs/status.md` 上，**多行 old_string（≥2 行、含中文/箭头/引号）反复匹配失败**，报错是 `Could not find the exact text`。但**同一文件里的单行 old_string 100% 成功**。

试过的组合：

| 尝试 | 结果 |
| --- | --- |
| 16 行大块替换（status.md 的 P1—P9 整表） | ❌ 失败 |
| 8 行块（status.md 的 P2—P9 六行） | ❌ 失败 |
| 3 行块（含 `→` `「」` `**`） | ✅ 成功 |
| 2 行块（含 `→`） | ❌ 失败 |
| 1 行块 | ✅ 全部成功 |
| 1 行块（内容一字不差的新旧串） | 返回"产生了相同内容"→ **说明这行是匹配上的** |

排查过的原因（**都不是原因**）：文件是纯 LF 无 CR（实测 `CR=0 LF=2080`）、引号是 ASCII 直引号（实测无 U+201C/201D）、没有 BOM 干扰。

**结论**：这是 edit 工具自身在长多行匹配上的不稳定，**不是内容问题**。

**解法（下次直接这么干，别再逐个试）**：

- **短块优先**：一律拆成 ≤3 行的块。表格行是 1 行 1 块，逐行改。
- **大段拼接用脚本**：把新内容写进 TEMP 里的 `.ps1`（**必须 UTF-8 with BOM**），用 `[System.IO.File]::ReadAllLines` 按行号切 + `WriteAllLines` 拼接，写完立刻 `ConvertFrom-Json` 验证。**本轮重写 `api.json` 的 `x-directions` 段就是这么干的**（`C:\Users\steam\AppData\Local\Temp\fix_api_tail.ps1`）。

### 3.2 改 `api.json` 时差点把 JSON 改坏

单行 edit 修一个数组元素时，我顺手在行尾加了个逗号 → 造成 `"...",\n],` 的**数组尾逗号**，**严格 JSON 不允许**，会让 `ConvertFrom-Json` 直接炸。

- **教训**：改 JSON 文件时，**行尾逗号是语义**，不是排版。改完必须立刻 `ConvertFrom-Json` 验一次。
- `check-contract.ps1` 第 11 项现在会验 `api.json` 可解析 —— 这个坑以后会被自动拦下。

### 3.3 分类体系这个坑（差点漏掉）

原先的认知闭环拆分里，「做的你」层的分类（技术实践 / 效率工具 / 认知方法论…）**默认成了后端内部实现**。但后端算出来的 `category_distribution` **前端要显示并高亮** —— **口径不一致前端就读不懂**。
