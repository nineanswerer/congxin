# 协作规范 — 两个人、两个 AI 平台、一份 Git 历史

> 这份文件回答一个问题：**我们各自用不同的 AI，怎么保证每次提交的上下文可控、不缺失？**
> 机制层面的细则在 `contracts/CONTRACTS.md`、规则在 `docs/adr/README.md`、模板在 `docs/handoffs/TEMPLATE.md`。

## 为什么要专门定这个

Git 记录的是"**改成了什么**"，不记录"**为什么这么改**"和"**试过什么失败了**"。
两个 AI 平台 = 两个互不相通的记忆体。如果只靠 GitHub 的版本控制，
换平台、换人、三个月后回看时，只能靠"读代码考古 + 猜对方意图"来恢复上下文——
每次重建要烧掉约 30% 的会话上下文，而且**猜得很自信**。

具体会出问题的四个地方：

| 问题 | 表现 |
| --- | --- |
| 让 AI 当考古学家 | 换个平台就重建一遍上下文，猜错也不知道 |
| 让 AI 写 commit message | 写出 `update model` 这种零信息量标题，git log 变装饰品 |
| GitHub 解决文本冲突，不解决语义冲突 | 两人各自"优化"同一模块，merge 后代码能跑但语义已错，`git bisect` 找不到元凶 |
| 没有 checkpoint 节奏 | 攒到最后一次性合并四条分支的差异，当场没法救 |

## 解法：上下文四层（全部进 Git）

```
L0 契约层  contracts/contract.json + CONTRACTS.md   ← 不可变事实，机器可读 + 自检
L1 身份层  AGENTS.md                                 ← 唯一真源，各 AI 平台文件只做指针
L2 决策层  docs/decisions.md + docs/adr/             ← 只增不改，"被否决的方案"不许空
L3 交接层  docs/handoffs/                            ← 每次会话一份，让 AI 自己写
```

- **L0 契约层**回答"什么东西改了会让另一个人的环境静默出错"（赛程、额度、技术底座、合规红线）。
- **L1 身份层**保证两个 AI 读的是**同一份**规则。`CLAUDE.md`、`.cursor/rules/`、`.gemini/settings.json`、`.aider.conf.yml`、`.github/copilot-instructions.md` **全部只是指针**，不复制正文——正文有两份就会互相漂移。
- **L2 决策层**把"为什么不那样写"钉死。**"被否决的方案"一节不许空**——只写结论的决策等于没写。
- **L3 交接层**是换平台前的读档点。**让 AI 写，人只审阅**——它刚有完整上下文，你没有。

## 三个动作（**其中两个已经自动化，不用人记**）

### 1. 换 AI 平台之前 → BOOTSTRAP（**已自动化**）

开工协议在 [`prompts/BOOTSTRAP.md`](../prompts/BOOTSTRAP.md)。
**各平台的指针文件会在打开仓库时被平台自动加载，并指向这份协议** → 新 AI 开工前自己读，
读契约 → 复述现状 → **停下来等确认**，然后才准改文件。

> 人手动整段粘贴仍然有效，但**已经不是必须动作了**。
> `git pull` 之后 `.githooks/post-checkout` 还会自动打印一份开工清单，提醒"契约变了要重读"。

### 2. 会话结束之前 → HANDOFF（**已自动化**）

按 [`prompts/HANDOFF.md`](../prompts/HANDOFF.md) 写一份交接到 `docs/handoffs/`。
这一步写在开工协议的「收工协议」段里，**AI 收工时自己会做**，重点是**"试过但没成的"**那一节。
**让 AI 写，人只审阅。**

### 3. 每次提交 → commit-msg hook 强制三行（**已自动化大半**）

```
<type>(<scope>): <祈使句意图>

Context: <为什么这么改>
Tried:   <试过什么、什么失败了>
Verify:  <怎么验证的>
```

安装一次：`powershell -ExecutionPolicy Bypass -File scripts/install-hooks.ps1`

**`Context:` 行由人给，但人不用手改 commit message。**
AI 把**人明确说过的**理由转录进 `.ctx/current.md`，`commit-msg` hook 在 `Context:` 缺失时**自动填入**；
提交成功后该文件自动清空。人没说过原因就留空——**AI 不许自己推断**，推断出来的 Context
只是 diff 的复述，看着煞有介事实则零信息量，还会污染下一个 AI。

> 剩下真正需要人参与的只有一件事：**跟 AI 说清"为什么改"**。一句话就够。
> `Tried:` 和 `Verify:` AI 自己写（它确实知道试过什么、怎么验证的）。

## 我们独有的优势：双模型交叉审查

别人只有一个模型，我们有两个。**两个模型的盲区不同**，交叉审一次能捞出单模型审不出的问题。

用 [`prompts/CROSS_REVIEW.md`](../prompts/CROSS_REVIEW.md)：把 diff + 契约喂给**另一个平台**的 AI，
让它用"挑错心态"审，重点找：违反契约、语义冲突、隐藏约束被破坏、上下文污染、假成功。

## 目录所有权（防冲突的第一道闸）

按**目录**分，不按文件分：

| 负责 | 范围 |
| --- | --- |
| `nineanswerer` | `server/`（知乎 API 对接、卡片生成、额度与缓存）、`docs/decisions.md`、`contracts/`、**`web/`（2026-11-18 起临时接管，见下）** |
| `5zdz5` | `assets/`、`docs/adr/`、`docs/handoffs/`、~~`web/`~~（**暂时交出**） |

### `web/` 临时接管（2026-11-18）

**为什么**：队友联系不上（11-17 起），而 **P3 明天 11-21 收口**——`web/` 是最后一块砖，
`web/` 还是零行，整个作品就没有可演示的东西。用户 2026-11-18 21:3x 拍板：
> 「队友那边先不管，你先弄一版能用的。」

**边界**：

1. **`web/` 由 `nineanswerer` 写**，`5zdz5` 回来后要改**走 PR**，不直推 main——
   避免两边 AI 各写一套前端、互相覆盖。
2. **只做「能演」的最小闭环**，不追求框架与工程完备：
   拖资料 → 咀嚼 → 吐卡片 → 点出处 → 知乎补观点 → 卡片列表；以及「照镜子」环节。
3. **渲染方案不变**（D29）：2.5D 用 **SVG + CSS `perspective`**；断层特写先做 CSS 强视差，
   **Three.js 真 3D 推镜留给队友**（保命砍法里它排最后）。
4. **素材仍走 D19**：官方刘看山 6 个状态动画 + 自建的 `eating` / `emitting` / `error` 过渡，
   **不自绘角色**；素材缺失时降级为静态占位。
5. 交接给队友时必须说明：哪些是「为了赶上 11-21 做的取舍」，哪些是「按 D29 必须保留的」。

**其他**：

- **同一文件同时只由一个人改。** 真要改对方的地盘，先在群里说一声。
- 共享区（`contracts/`、`docs/status.md`、`README.md`）改动**默认直推 main**，不走 PR
  （用户 2026-11-19 拍板，见 [decisions.md](decisions.md) D41）。
  - **前提**：队友仍联系不上，**且**处在交付窗口内（P3 收口 / 提报前）。
  - **队友回来、或他明确要看 diff** → 改走 PR 再合并。
- 推送频率：**每天至少推送一次**，不要攒到最后。

## 分支模型

```
main            始终可跑，禁止直接推（除文档）
  ├─ feat/<模块>-<短描述>     一个人的一条线，做完发 PR
  └─ fix/<模块>-<短描述>
```

- 一条分支只做一件事，**不要把两个人的改动揉成一次提交**——谁的改动谁的提交。
- PR 用 [`.github/PULL_REQUEST_TEMPLATE.md`](../.github/PULL_REQUEST_TEMPLATE.md)，里面含自检清单和交叉审查栏。

## 提交前自检

```powershell
powershell -ExecutionPolicy Bypass -File scripts/check-contract.ps1
```

检查：contract.json 可解析、必备文件齐全、AGENTS.md 行数不超上限、**疑似密钥扫描**、
.gitignore 覆盖凭证、关键日期与 status.md 一致、hook 是否安装、是否有交接记录、
各平台指针文件能否走到开工协议、post-checkout 是否带开工清单、
**API 契约 api.json 是否可解析且核心接口齐全（出处必填 / user_hint 必填 / empty 必填）**。
**FAIL 就不能提交。**

## 官方要求的"创作佐证"怎么落

官方明确建议保留 **AI 交互记录、设计底稿和开发日志**。这套机制刚好覆盖：

| 官方要的 | 在我们仓库里对应什么 |
| --- | --- |
| AI 交互记录 | `docs/handoffs/`（AI 自己写的交接）+ 两个 AI 平台的 commit 轨迹 |
| 设计底稿 | `contracts/`、`docs/brief.md`、`docs/adr/`、`docs/decisions.md` |
| 开发日志 | Git 提交历史 + `docs/status.md` |

**两个 AI 平台一起干活不是风险，是可以拿出来讲的创作佐证。**
