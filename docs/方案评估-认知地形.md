## 1. 一句话结论

**方向换是对的（他这个确实比"资料→卡片"更有想象力），但形态必须做一次收敛。**

## 2. 我认可的四点（这是构想的真价值）

### 2.1 "标签是起点假设，不是终点结论"

这不是包装话术，是**产品范式的转变**——把"测量—归类"换成"假设—碰撞—对照—修订"。
而且它和官方能力清单**咬合得极准**：官方给"问题发现"这一项能力写的产品定位原文就是"**观点对照**"（rules 11.5）。整个"认·清"构想，本质上就是把这句官方定位做成了一个产品。

### 2.2 "不一致是最有价值的信号"

这是真正的产品洞察。传统 MBTI 把偏差当**误差**要修正；这里把偏差当**最值钱的地标**。
这个转换一旦成立，直接改变产品的价值主张——从"告诉你你是谁"变成"带你看清你说的你和做的你差多远"。

### 2.3 桌宠当向导，不是测试员

比"卡片生成器 + 宠物皮肤"更有人格、更贴 **AI × 陪伴与交互** 赛道（S3 首次单列，有 ¥2,000 最佳交互陪伴奖）。
刘看山从"一个贴在角落的动画"升级成"带路的角色"，**这正是 D14「桌宠是主体」的加强版，不是违背**。

### 2.4 情境题来自知乎真实讨论 —— 这条**立得住**（实测）

见第 3 节实测 B。知乎站内**确实有**大量高信号的 MBTI / 自我认知讨论，问题发现接口一次就能捞到真实问题标题 + 完整 URL。

## 3. 必须纠的三处（硬事实，不是意见）

### 3.1 ❌「知乎直答 Agent DEEP_SEARCH」这个能力**不存在**

**实测 A（2026-11-17 16:2x 与 16:5x，两次，消耗直答 2 次）**：

**第一次** —— `POST /v1/chat/completions`，`model=zhida-agent`，问"列出知乎站内关于 MBTI 标签局限的真实问题标题"。

> 模型回答：**"我无法访问知乎站内的问题列表，也无法进行深度检索"**，
> "我没有权限访问知乎平台上的实时用户提问数据" → 随后给出 **8 条它自己编的"典型问题范式"**（如"MBTI 会不会正在成为另一种刻板标签"），**不是真实标题**。

**第二次（决定性测试）** —— 问"请检索知乎站内关于'如何认清真实的自己'的问题与高赞回答，并给出原问题的完整链接"。

> 模型回答：**"我无法获取与知乎内容直接相关的实时检索结果，也不具备保证输出链接的真实性与准确性"**，
> 建议用户"打开知乎 App 或官网，在搜索框输入……" → **返回文本中零个 `zhihu.com/question/...` 链接**（正则扫描确认）。

> ⚠️ **注意官网宣传与实际能力的差距**：官网「技术支持」板块对直答 Agent 的描述是
> **"先检索知乎相关内容，再生成有依据、可追溯的自然语言回答"**——这是产品宣传口径。
> 实测结论要更精确：**它会参考知乎内容来生成回答（作为改写者可用），但它给不出"真实问题标题 + 可点击回跳的原问题 URL"这两个字段。**
> 而"情境题来自知乎真实讨论"这个需求，**恰恰必须有这两个字段**（否则卡片无法回溯出处，与 D12 的技术基础冲突）。

**正确链路（本项目已实测可行）**：

```
问题发现  GET  /api/v1/user/question_recommendations?Query=<主题>&Count=N   → 真实问题标题 + 完整 URL
   ↓
回答摘要  GET  /api/v1/content/question_answers?QuestionUrl=<完整URL>          → 真实回答摘要 + 原回答链接
   ↓
情境题生成 POST /v1/chat/completions（zhida-fast-1p5 或 zhida-thinking-1p5）  → 把上面两段真实材料改写成情境题
```

> **直答的角色是"改写者"，不是"检索者"。** 它拿到上面两段真实材料后再生成情境题，质量会明显高于让它凭空编题。
> ⚠️ **"情境题生成"是产品的核心工程，必须自己写 prompt 并反复调**，不能指望直答 Agent 一键出好题。
> 这是新方案里**最重的一块工程**，排期时别当成"调个 API"。

### 3.2 ⚠️ 行为数据拿得到，但 OAuth 拿不到，要用 Access Secret 读

**官方能力清单里有**（rules 11.5 / 12.2）：

| 能力 | CLI 命令 | 额度类 |
| --- | --- | --- |
| 我的创作 | `zhihu-cli me contents` | `creator`（500/天） |
| 我的关注 | `zhihu-cli me followees` | `user_data`（10000/天） |
| 我的收藏夹 / 近期收藏 | `zhihu-cli me favorites lists/items/recent` | `user_data` |
| 本人全文、评论、账号统计、单篇统计 | `zhihu-cli me content/comments/stats/content-stats` | `creator` |

**所以"做的你"三层数据是齐的**：收藏跨度（我关注/收藏的是不是结构化规划、效率工具）、关注对象类型、创作中的论证结构——全部可读。

**但 OAuth 那条路要额外一步**（rules 12.3 原文）：读授权用户的创作/关注/收藏，需要
`Authorization: Bearer <Access Secret>` + `X-OAuth-Token` + `X-Request-Timestamp`。

**排期含义（重要）**：
- **开发期（P2—P6）用 Access Secret 读**账号自己的 `me followees` / `me favorites` / `me contents` 来验证行为对照算法——**现在就能做，不用等 OAuth**。
- **12-05 拿到 OAuth 凭证后**，换成登录用户的数据。两者是**同一套接口形状**，**不返工**。
- 但 OAuth 联调本身仍压到 12-05 之后（App ID / App Key 是创建项目后才分配），这段必须用 mock 顶。

### 3.3 ⚠️ 刘看山**没有 3D 模型**

官方素材包实况（`assets/kanshan/` 与 `docs/sources/kanshan_material/`）：

| 有什么 | 规格 |
| --- | --- |
| 6 个动态动作 | 2D 序列帧 sprite，1536×1872 / 8列×9行 / 每帧 192×208（`idle` `greet` `thinking` `cheer` `sleep` `play`） |
| 3 张三视图 | JPG 设定稿（front / side / back），**是给人看的参考图，不是可渲染的 3D 资产** |

**含义**：3D 化 = **自建角色** = 建模 + 绑定 + 动画适配 ≈ **20—30 人时**，而且直接违反 D19 已定的处理方式（"**不自绘角色**，用 CSS 过渡与状态气泡补官方素材缺的三个核心动作"）。

**可行降级**：2D 序列帧贴进场景做 **billboard**（永远面向相机），走路时播对应帧。成本 ≈ 1 人时，但"走过去看"时它不转身会露馅。

## 4. 真正的风险不是"3D"，是"3D 能不能让评委看懂"

### 4.1 权重摆在那里

| 维度 | 初审权重 | 决赛权重 | 3D 对这一项是加分还是减分 |
| --- | --- | --- | --- |
| AI 场景价值 | **40%** | 35% | 不变（靠内核，不靠 3D） |
| 创新度 | 25% | 25% | **加分**（但见 4.2） |
| 完成度 | 25% | 25% | **减分**（3D 是最容易做不完的地方） |
| 产品体验与设计感 | 10% | 8% | **加分** |
| 计划书和演示环节 | — | 7% | 不变 |

### 4.2 创新度有个反直觉的坑

> "3D 不是皮肤，是数据的表示方式。断层的位置来自行为对照的结果，塔的高度来自回答的倾向性。"

这句话**评委在 5 分钟 Demo 里验证不了**。"塔的高度来自回答倾向性"需要评委心领神会，实际演示时他只会看到"有个 3D 场景"，**看不到信息性**。
要让他看出来，需要额外约 30 秒解释——**那 30 秒是从 Demo 主体里偷的**。

**而且"让用户走过去就看见了"在实际使用中可能变成"用户走丢了"**：
评审点开链接只有 3 分钟，进到一个自由漫游的 3D 场景里，他得自己转镜头找断层。**分层地图一眼就懂，自由漫游可能什么都看不懂。**

### 4.3 手机

目标用户 22—30 岁，主战场是手机；人气奖产出（12-05—12-19 活动广场的点赞/使用/评论）几乎全靠手机访问。
**3D 在手机上的性能与操作都不占优**。官方允许网页，所以应做 Web；"纯软件端桌面 3D 程序"会直接放弃手机这半边市场。

### 4.4 完整人时估算（诚实版）

| 工作块 | 人时 | 性质 |
| --- | --- | --- |
| MBTI 自评问卷 + 假设输入 | 0.5 | 编码 |
| **情境题生成链路 + prompt 调优** | 4—6 | **工程 + 反复调** |
| **行为对照算法**（收藏/关注/创作 → 认知特征 → 与自报类型比对 → 张力信号） | 4—6 | **设计为主** |
| **地形生长规则**（回答 → 空间参数映射） | 4—6 | **设计为主** |
| 3D 场景 + 漫游相机 + 刘看山 billboard + 状态机驱动 | 8—12 | 编码 |
| 断层/桥的空间表达 | 2—3 | 编码 |

→ **全 3D 正好卡在区间上沿，且其中两块（行为对照算法、地形生长规则）是设计工作不是编码工作，最难在几天内出成果。**
→ 对照：现方案（学习桌宠）P2—P9 全是**已知且可预估**的工作。

## 5. 推荐方案：保内核，换形态（2.5D 分层认知地图）

### 5.1 不变的（创新点，一点不改）

- 三层结构：**说的你**（自报类型 → 中央初始地形）、**做的你**（OAuth 行为数据 → 行为地貌）、**情境下的你**（每答一题长一块）
- 三者关系：**重叠 / 错位 / 断层 / 桥** = "认清"本身
- **断层是产品主角**，不是误差
- 桌宠是向导，不是测试员
- 情境题来自知乎真实讨论
- 匹配依据是认知过程，不是标签

### 5.2 换的（呈现层，不是信息层）

**从"自由漫游三维空间" → "可展开的分层认知地图 + 镜头推近"**

| | 自由漫游 3D | 分层认知地图（2.5D） |
| --- | --- | --- |
| 技术 | Three.js / R3F + 漫游相机 + 地形生成 | **SVG + CSS `perspective` + `transform`**，已定 D11 路线内 |
| 成本 | 12—18 人时 | **3—5 人时** |
| 刘看山 | 要么建模（20—30 人时）要么 billboard 露馅 | **2D sprite 直接放，零成本零破绽** |
| 评审 3 分钟能看懂吗 | 可能走丢 | **一眼看懂三层 + 断层** |
| 手机 | 性能与操作都吃亏 | **能用** |
| "走过去看" | 真漫游 | **推近 + 视差 + 断层特写**，保留隐喻 |

**外加一条真 3D 的彩蛋（2—3 人时，只用在一处）**：
最终 Demo 里"断层"那一段，用 Three.js 做一次**真实推镜**（相机从远处推向断层）。
> 大部分界面是 2.5D，但断层那里是真的 3D——**这个反差本身就是记忆点**，而且把 3D 的成本压到了最低。

### 5.3 砍掉（明确不做的）

| 砍掉 | 理由 |
| --- | --- |
| 自由漫游（键盘 WASD / 大范围旋转） | 成本高、易走丢、评审看不懂；改成"分层展开 + 推近" |
| 刘看山 3D 建模 | 官方无 3D 资产，自建违反 D19 且人时爆炸 |
| 基于认知过程的**他人匹配** | 需要用户池 + 行为数据聚合，冷启动没人；写进"后续规划" |
| 导出录屏 | 快照就够，录屏是额外工程 |
