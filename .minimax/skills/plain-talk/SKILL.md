# 说人话（plain-talk）

把技术产出翻译成人话。**人话 = 术语没了，事实一个不少。**

## Inputs to collect

- **给谁看**：用户自己 / 队友 / 评委 / 未来的自己。用户没说就从上下文判断（"发给队友"→转发版），并在开头一行注明「这是给 X 看的版本」。
- **原文**：要翻的那段产出。找不到原文时先问，别凭印象转述。

## Procedure

1. **先抽事实清单**——原文里的事实分两类：
   - **限定类**（丢了就变成假话，**一个都不能少**）：数字与单位、状态（已完成 / 未验证 / 失败 / 计划中 / 阻塞）、时间点与截止日期、限定条件（「仅在……时」）、错误码与提示文案的原话、谁要做什么。
   - **信息类**（读者靠它判断轻重，**别整段丢**）：今天修好了什么、还欠着哪几件、哪些已经验过、哪些还没验过。
   原因：限定类决定成品可不可信；信息类决定读者能不能自己判断轻重。只留结论、把「今天修了 9 处、还欠 4 件活」这类清单丢掉，读者就没有判断依据了。

2. **能核就核，别只转述**：
   - 原文里的数字如果核得动（读文件、跑 git、调不耗额度的接口），核一遍再说；核不动就标一句「这是原文说的，我没核」。
   - 核出来和原文对不上，**以你核到的为准并说明差异**，不要替原文圆场。
   原因：人话版的价值在于可信。只把难懂的话换成好懂的话、事实一条不核，那还是一份不敢当真的汇报。

3. **映射术语**——读 `references/glossary.md`：
   - 命中 → 换成人话（术语表里带「人话」列，直接用）。
   - 没命中 → 用通用说法，**首次出现时括号留一次原词**（例：「额度组（每天 100 次的那组调用次数）」）。
   原因：团队里不同人熟悉不同模块，留一次原词对方才搜得到出处。

4. **搭结构**：
   - 第一行：**一句话结论**——这件事到底是什么状态。
   - 然后 3—6 条展开，每条一个意思。
   - 有活要人干的，单列一段「需要谁做什么」。
   - 原文里两类事都有时，**显式分开说**：「坏了的」和「还没做的」——用户最常问的就是这个区分，混在一起读者会以为一切正常，或以为一切坏了。
   - 「风险 / 未验证」**只在真有内容时写**，没有就整段删掉（凑数比不写更糟）。
   原因：读者要的是"所以呢"，第一行就得给答案。

5. **把数字念出来**：
   - 「额度 0/100」→「今天的调用次数已经用完，明天 0 点恢复」
   - 「PASS 13 / WARN 0 / FAIL 0」→「13 项检查全过，没有警告也没有失败」
   - 「14 个路径」→「前后端约定好的 14 个接口」
   原因：数字本身不解释，读者要的是它意味着什么。

6. **语气**：像同事之间讲话。不用「赋能 / 闭环 / 抓手 / 链路打通」这类词；不用感叹号；不为了显得专业而保留英文缩写（`schema`、`envelope` → 能用中文说就用中文说）。

7. **收尾对账**：对着第 1 步的事实清单逐条勾，缺一条就补回去。特别检查这几个最容易翻错的地方：
   - 「未验证」有没有变成「已通过」
   - 「额度 0/100」有没有变成「额度有点紧」
   - 「发现并修了 3 个 bug」有没有变成「3 个 bug 都好了」（没验证过就不能这么说）
   - 「计划做」有没有变成「已经做了」
   - 信息类事实有没有被精简掉（今天修了什么、还欠哪几件）

8. **可选第二遍**：本机若装了 `humanizer-zh`，成稿后再用它那 31 条过一遍，去掉 AI 腔。
   **只去腔，不动事实**——它的规则里「保留信息和确定程度」优先级最高，这条同样适用于这里。

## Output contract

- **默认给「人话版」**：一句话结论 → 展开 → （需要谁做什么）→ （风险与未验证）。
- 用户说「发给队友 / 发给评委 / 能直接发出去」时，**再给一版「可转发版」**：
  - 去掉内部术语、流程黑话、开发细节（commit hash、内部文件名等）
  - **保留全部日期、数字、截止时间、动作项**
  - 不夹带解释性括号、不带「（由 AI 整理）」这类尾巴
  - 结尾给明确动作项和回复期限
- 用户贴来的材料**本来就是给别人看的**（队友、评委、群里），直接给两版，别等用户再问一次。
- 错误提示文案翻人话时：**只能去掉术语，不能把话翻得更好听但更假**。「额度用完了」不能翻成「网络不稳定」。

## Failure handling

- **原文本身有矛盾或缺数据**：直接说「这段我没核实」并指出矛盾点，**不要为了读起来顺而圆场**。按项目纪律，失败与未验证的数据要显式标注。
- **原文是纯代码 / 日志且没有结论**：先用一句话说明「这段在干什么」，再翻关键部分；不要逐行翻译。
- **判断不了给谁看**：按最可能的读者出一版，并在开头注明假设，让用户一句话就能纠正。
- **翻译后发现信息不够**：宁可回问，也不要补一个看起来合理的说法。
- **别把精简做成删信息**：精简是换说法，不是换内容。读者判断轻重靠的是「今天修了什么、还欠哪几件、哪些没验过」这类清单，删掉它整段就没用了。

## Examples

**Input**（AI 收工报告里的一句）：
> 问题发现额度 0/100，明早跑 `node scripts\regress-p3.js`，上次 13/14，唯一 FAIL 是额度耗尽。

**人话版**：
> 今天的知乎调用次数已经用完了，明天 0 点恢复。明早跑一遍完整回归看看有没有问题——上次 14 项里过了 13 项，没过的那项就是撞上额度用光，不是真 bug。

**可转发版（给队友）**：
> 今天把知乎的调用次数用完了，明天 0 点恢复。明早我跑一遍完整回归（14 项）。上次除了额度用光那项，其余都正常。

差别在最后一句：额度耗尽**不是** bug，翻成人话时不能变成「有一个功能坏了」。
